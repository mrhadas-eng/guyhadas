`keywords`: `sources` (per source: sourceProperty, report, volume, difficulty, competition, position, url, metrics, timesSeen, firstSeenAt, lastSeenAt), `sourceList`, `seedRefs`, `grouping {rule, score, topicTitle}`, `excludedByRule {ruleId, rule, reason}`, `firstDiscoveredAt`, `lastDiscoveredAt`. No new collections, no new indexes (all new queries are equality-only), no rule changes.

## Decisions (ADR log)

1. **Seeds are rebuilt server-side; the client sends only a `seedKey`.** Guarantees discovery is driven by the confirmed Service Map, never by typed text. Cost: one extra Firestore read pass per run (free).
2. **Seeds are computed on demand, not persisted as a collection.** They are a pure function of confirmed services + profile + rules; persisting them would create a second source of truth. Lineage is persisted where it matters — on the raw queries and topics (`seedRefs`).
3. **Website/AI geography becomes a target only on ≥ 3 crawled pages** (`minPagesForServiceArea`, configurable). A single portfolio project is typically one page plus maybe a listing; three pages is a conservative, explainable proxy for "area the business presents as served". The owner can always declare an area in the profile.
4. **Script-mismatch guard.** "עיצוב פנים Caesarea" is not a real search; such combinations are skipped and explained rather than silently translated.
5. **Semrush split into seed and domain operations.** Previously every seed re-bought the domain's own rankings and competitors (~900 of ~2,100 units). Cache identity for seeds is phrase + database only, so the same phrase reached from two services is paid once.
6. **Grouping anchored on the topic title, exact match first, place guard.** Fixes drift (matching against accumulated tokens) and city collapse ("עיצוב פנים קיסריה" vs "…חיפה"). Still deterministic, still no stemming.
7. **A re-found query keeps its existing topic.** This is what makes owner exclusion durable for exact repeats; close variants that group into an excluded topic also stay excluded.
8. **Qualification never decides.** It is shown as hints with reasons; owner status is the only decision and discovery never writes it.

## Semrush V4 Keyword Metrics pilot (2026-10, narrow, owner-gated)

- **Enrichment, not discovery.** V4 Keyword Metrics adds market-demand evidence to ONE query that already exists in an approved Search Topic. It creates no topics or keywords, expands no seeds, makes no domain reports, and is not a discovery source (`sourceList` / `sources` are untouched). The V3 discovery adapter (`functions/semrush.js`) and its functions are unchanged and are not used.
- **Cost.** One request = **20 API units** (developer.semrush.com "Get keyword metrics", verified 2026-10-13; V4 Early Access). Governed operation `semrush.enrichKeywordMetrics` (`apiLimits.js`):
  - hard 20-unit per-call cap, enforced by `runGoverned` before the call. A missing or higher estimate is `blocked_by_budget`.
  - quotas: 1 provider call per business per day, 5 per month, 2/10 globally.
  - cache first: identity = business + normalized keyword + country + month + provider version. A cache hit costs 0 units.
  - fail closed; circuit breaker; ledger rows carry `providerCalled`, `estimatedUnits` and `providerUnitsUsed`.
  - a failed request records `providerUnitsUsed: null`, because Semrush does not document whether failed requests are billed. It still counts toward the quota.
- **Intentionally limited.** One keyword per invocation and at most one Semrush request per invocation. No batch, no retry, no forceRefresh, no schedule, nothing on render. The owner must confirm explicitly (`confirmPaidCall: true` from the second button).
- **Files.**
  - `functions/semrushV4.js`: adapter. Authorization header only, one fetch, provider-neutral mapping.
  - `functions/keywordMetricsStore.js` and `functions/keywordMetrics.js`: `visibilityEnrichKeywordMetrics`.
  - UI: the "בדיקת Semrush לנושא" control inside an expanded approved topic card.
  - Tests: `functions/test/keywordMetrics.test.js`.
- **Storage.** `keywords/{id}.marketDemand` holds the provider-neutral fields `{keyword, country, month, searchVolume, keywordDifficulty, intents, competitiveDensity, cpc (USD), numberOfResults, serpFeatures, trends, metricsAvailable, dataQuality, kind: "market_demand_estimate", source: "semrush_v4", retrievedAt}`.
  - It is server-written only: Firestore rules forbid any client create or update of the field.
  - It is labelled as a market-demand estimate, never as observed Google traffic. Search Console evidence is not touched.
- **Downstream stays provider-neutral.**
  - M4 `topicIntelligence` reads `marketDemand` as the same per-query `{volume, difficulty}` market-demand evidence as before. For that query it takes precedence over V3 evidence, and `demandProvenance` is added only when V4 contributed.
  - M5 scoring and M6 decision semantics are unchanged.
  - To see an effect: enrich → run M4 → run M5 → run M6.
- **Known interpretation caveat (#55).** M5 tiers market demand relative to the other enriched topics. With a single enriched topic, any positive volume becomes the top tier.
- **Unit reconciliation (#56).** The ledger records the documented price. Verify the actual charge against the Semrush API query log and, once it works, the balance check.
